# Pluggable external token validator for the Entra ID providers — design

Request: "REQUEST PUSH seam" (2026-11-27). Component: push-auth (`crates/push-auth-core`),
Helm chart `deploy/helm/push-messenger`. Opt-in; with `PUSH_ENTRA_VALIDATOR_URL` unset no
code path, log line or chart output changes.

## Decisions

| # | Decision | Why |
|---|---|---|
| V1 | `EntraSettings` gains `pub validator: Option<ValidatorSettings>` (`url`, `timeout`, `secret`), parsed by `EntraSettings::from_lookup`, so wrappers using `EntraSettings::from_env` get it too. `ValidatorSettings` has a hand-written `Debug` that redacts the secret. | One place reads every `PUSH_ENTRA_*`; config.rs already reads it only with `entra`/`entra-app`. |
| V2 | `PUSH_ENTRA_VALIDATOR_URL`: trimmed, empty = unset. Absolute URL; `https://` anywhere, `http://` only for `127.0.0.1`, `[::1]`, `localhost` (as `PUSH_ENTRA_AUTHORITY_HOST`); no user info, no fragment; a path and query are allowed. | Spec §2.2. User info could hold a password, so it is refused (and then not echoed). |
| V3 | `PUSH_ENTRA_VALIDATOR_TIMEOUT_MS`: whole number 100–10000, default 2000. `PUSH_ENTRA_VALIDATOR_SECRET_FILE`: read once at start-up; trimmed content must be 1–1024 visible ASCII characters (a valid header value); errors name the variable and the path, never the content. Both are refused (`ConfigError::Invalid`, "set only with PUSH_ENTRA_VALIDATOR_URL") when the URL is unset. | Spec §2.2; a secret or timeout without a URL is a misconfiguration that would otherwise be silently ignored. The variables are new, so no existing deployment is affected. |
| V4 | `EntraSignIn` holds `keys: Option<Arc<KeySets>>` and `validator: Option<Arc<Validator>>`, exactly one set. With a validator no `KeySets` is built and `warm()` does nothing. | Spec §2.1: the validator owns key discovery. |
| V5 | `verified(token, ProviderKind)`; `ProviderKind::{User, App}` (`"entra"`, `"entra-app"`), crate-private. Pre-checks in both modes: size, three segments, header JSON with `alg` RS256 and a `kid`, unverified `tid` admitted, unverified `iss` = the tenant's v2.0 issuer. Then either JWKS + `jsonwebtoken::decode` (unchanged) or the validator. | The header check is local, cheap and only narrows (a validator can never make push-auth accept `alg: none`). |
| V6 | Request: `POST url`, `Authorization: Bearer <token>`, `Content-Type`/`Accept: application/json`, `X-Push-Validator-Secret` only when configured, body `{"provider":"entra"\|"entra-app"}`. No `X-Request-Id`: push-auth has no request id (optional in the spec). reqwest client: `redirect::Policy::none()`, `timeout` = `connect_timeout` = the configured timeout, `no_proxy()` for loopback URLs (a pod's `HTTPS_PROXY` must not catch the sidecar), env proxies otherwise. No retries. | Spec §2.3. |
| V7 | Response handling. Every body is read by chunks up to 16 KiB (a larger `Content-Length` or body is `Unavailable`). **200**: not JSON → `Unavailable`; JSON not of the schema (no `claims` object, a required claim missing, a claim of the wrong JSON type) → `Rejected(Malformed)`. **401**: JSON `{"reason": <name>}` with a known `Reason` name → `Rejected(reason)`; anything else (no body, other JSON, unknown name) → `Rejected(Validator)`. **Any other status** (3xx included), timeout, connection error → `Unavailable` with only "HTTP <code>", "timed out", "could not be reached" or "failed". The 200 `Content-Type` is not checked. | Spec §2.4. |
| V8 | Defensive re-checks of returned claims, in order: schema (V7) → `tid`/`oid` equal to the token's unverified `tid`/`oid` (else `malformed`) → `tid` admitted (`tenant`) → `iss` = the tenant's v2.0 issuer (`issuer`) → `aud` (string or array) contains a configured audience (`audience`) → `exp < now - 60` (`expired`) → `nbf > now + 60` when present (`not_yet_valid`). `nbf` is optional, as in the spec's schema. Then the same `EntraClaims` deserialization, `claims::common` and provider policy as today; the returned claims object is the principal's verified claims. | Spec §2.4 1–4; a validator can only narrow who signs in. |
| V9 | `Reason::Validator` (`"validator"`), and `Reason::from_name` for the 401 mapping. | Spec §2.4. |
| V10 | Security log: `auth.entra.rejected` (entra) and `auth.external.rejected` (entra-app) carry `validator = true` only in validator mode: the field is an `Option<bool>`, so built-in lines are byte-for-byte unchanged. The middleware learns the mode from `IdentityState.validator`, set in `api::router` from `Auth::external_validation(provider)` (true only for the built-in `entra`/`entra-app` authenticators with a validator). `EntraSignIn::verify` logs the same way. Unavailability in validator mode is logged as "the token validator is unavailable" with the error kind/status only. | Spec §2.4 error semantics. |
| V11 | Test stub `StubValidator` in `entra/testing.rs` (feature `testing`): axum on 127.0.0.1; by default echoes the bearer token's unverified payload as `claims` (a validator copies claims); can answer a fixed status/body, fixed claims, or wait; records each request's method, authorization, secret header and body. | Spec §5. |
| V12 | Helm: `auth.signIn.entra.validator.{url,timeoutMs,secretFile}` → the variables (only with an Entra provider and a URL); `auth.extraContainers`, `auth.extraVolumes`, `auth.extraVolumeMounts` rendered verbatim (`toYaml`) into the auth Deployment; `validate.yaml` fails on a validator URL that is `http://` to a non-loopback host or not http(s), a `timeoutMs` outside 100–10000, a relative `secretFile`, and extras that are not lists. Defaults render byte-for-byte as before. Network policy unchanged. | Spec §2.5. |
| V13 | No caching of validator results or failures; one validator call per sign-in; never a JWKS fallback. | Spec §2.4. |

## Addendum: header (forward-auth) protocol — request "REQUEST PUSH headers" (2026-11-27)

The follow-up request supersedes the first one: it restates it and adds
`PUSH_ENTRA_VALIDATOR_PROTOCOL = json | headers`. Decisions V1–V13 stand, refined by:

| # | Decision | Why |
|---|---|---|
| H1 | `ValidatorSettings` gains `protocol: Protocol { Json, Headers }` (default `json`, value case-insensitive), `request_headers: Vec<(HeaderName, HeaderValue)>`, `correlation_header: Option<HeaderName>` (default `X-Request-Id`; set but empty disables), `claim_prefix: String` (default `Subject-Token-Claim-`, lowercased), `encoded_claim_prefix: Option<String>` (default `Subject-Token-Encoded-Claim-`; set but empty disables). All are refused when set without a URL (as V3). | §6. |
| H2 | `PUSH_ENTRA_VALIDATOR_REQUEST_HEADERS`: a JSON object of string values when it starts with `{`, else `Name: value` pairs separated by newlines or `;`; empty entries skipped. Names: RFC 9110 tokens, unique case-insensitively, at most 32; values: trimmed, 1–1024 characters of visible ASCII or inner spaces/tabs. Reserved (case-insensitive): `Authorization`, `Original-Uri`, `Original-Method`, `X-Forwarded-For`, `Host`, `Content-Length`, `Content-Type`, `Accept`, `Transfer-Encoding`, `Connection`, `X-Push-Validator-Secret`, `TE`, `Upgrade`, `Expect`, `Keep-Alive`, `Proxy-Authorization`, `Proxy-Connection`, `Trailer` and the correlation header. In the text form `;` separates entries, so a value containing `;` needs the JSON form (the chart always renders JSON). Errors name the variable and the offending header *name*; the value is shown as `<redacted>`. | §3.1, §6, §8 (never echo header values). |
| H3 | `RequestMeta { original_uri, method, client_ip, request_id }` (all `Option`), public in `crate::identity`. `Authenticator` gains a defaulted `authenticate_with(&self, token, &RequestMeta)` that calls `authenticate`; the identity middleware calls `authenticate_with`, and `EntraSignIn`/`EntraAppSignIn` override it. Original-Uri = `PUSH_AUTH_PUBLIC_URL` (without trailing `/`) + the request path, no query; the client IP is the one the rate limits use; the request id is a fresh UUID v7 per sign-in attempt. Any value that is not visible ASCII is omitted. | §2, §3.1, §8. Additive to the public trait: external authenticators are unaffected. |
| H4 | Both protocols send `Authorization`, the secret, the correlation header (when enabled and a request id exists), `Original-Uri`, `Original-Method`, `X-Forwarded-For` (each when known) and the static headers. JSON additionally sends its JSON body and content headers; headers sends `POST` with an empty body and `Content-Length: 0`. | §3.1, §4. |
| H5 | Headers protocol, responses: 2xx → claims from headers; 401 and 403 → `Rejected(Validator)`; everything else → `Unavailable`. The body is drained up to 4 KiB and ignored. The `error` parameter of `WWW-Authenticate` (visible ASCII, at most 64 characters) is logged at info level with the status; nothing of the answer reaches the client. | §3.2. |
| H6 | Claim headers: a header whose lowercase name starts with the encoded prefix (checked first, when enabled) or the plain prefix; the rest of the name (lowercased) is the claim name; an empty rest is malformed. At most 64 claim headers, each value at most 8 KiB, at most 32 KiB of claim header names plus values, checked before any decoding → `Unavailable` and a warn log. Plain values must be visible ASCII/spaces; encoded values are base64 (standard or URL-safe, padding optional) of UTF-8. If a claim has an encoded header, only its encoded headers count. | §3.3. |
| H7 | Typing: `exp`/`nbf`/`iat` one value, an optionally signed decimal integer → number; `roles`/`aud` and any claim whose (single) value starts with `[` are multi-valued: each header value is a JSON array of strings (if it starts with `[`) or split on commas and whitespace, empty items dropped, all headers concatenated; `roles` is always an array, `aud` a string when it has one item; `scp` the same items joined by one space; every other claim exactly one header, trimmed string. Violations → `Rejected(Malformed)`. | §3.3. "Malformed" in §3.3 is read as the rejection reason (§3.3 says so explicitly); §3.2's "malformed claims → unavailable" is taken to mean undecodable *responses* (limits), which are unavailable. |
| H8 | Re-checks shared by both protocols (V8) gain: `sub`, when the returned claims have it, must equal the token's unverified `sub` (malformed otherwise). `ver` is required by the JSON schema (as before) but optional in the headers protocol: an answer without `ver` takes the presented token's unverified `ver` (when a string; the validator has verified the token, so its payload is authentic), and a returned `ver` is kept. A `ver` other than `2.0`, or none in the answer nor the token, is refused by `claims::common` as `version` (spec §3.3: `ver`, when present, must be `2.0`). | §5, §3.3. |
| H9 | Start-up warning (once, when the verifier is built) when the protocol is `headers` and no request headers are configured. | §3.3. |
| H10 | Helm: `validator.protocol` (json), `correlationHeader` (X-Request-Id), `requestHeaders` (map, rendered as a JSON object with sorted keys via `toJson`, so a value may contain `;`), `claimHeaderPrefix`, `encodedClaimHeaderPrefix`. With a URL the chart renders PROTOCOL, TIMEOUT_MS, CORRELATION_HEADER (also when empty, which disables it), SECRET_FILE and REQUEST_HEADERS when set, and the two prefixes when the protocol is headers. `validate.yaml` refuses an unknown protocol, a bad timeout, bad header names/values, reserved names (the same list as auth-svc, H2), a non-token correlation header or prefix, and an encoded prefix that begins the plain one (equal or a prefix of it, case-insensitively — the rule auth-svc applies). Defaults render byte-identically. | §7. |
| H11 | Module layout: `entra/validator/` with `mod.rs` (client, both protocols), `config.rs` (settings parsing), `claims.rs` (schema and re-checks), `headers.rs` (claim header decoding). | Keeps each file focused. |
