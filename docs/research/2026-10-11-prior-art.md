### 0.2 Meta chose MySQL, not a log

The brief implied Kafka/log-style for per-user inboxes. Meta explicitly **evaluated and rejected** that:

> "We looked at several existing technologies to support the queue's backing store, but couldn't find anything that met our needs in terms of scale, reliability, speed, and flexibility. **Ultimately, we opted to build the queue storage on top of MySQL and flash.** For MySQL we decided to use semi-sync replication, which can give you durability across multiple servers… we can handle database hardware failures in **under 30 seconds**, and the latency for enqueueing a new message is **an order of magnitude less** than writing to the traditional disk storage."

— https://engineering.fb.com/2014/10/09/production-engineering/building-mobile-first-infrastructure-for-messenger/

**Means today:** a relational per-recipient inbox is the *validated* shape at planet scale, not a starter-kit compromise. Starting on Kafka/Cassandra for one small AKS node is unjustified.

### 0.3 XEP-0333 was narrowed and renamed

It is **"Displayed Markers"**, not "Chat Markers". `<received/>` and `<acknowledged/>` were **removed**:

> "Earlier drafts of this specification included `<received/>` and `<acknowledged/>` with the same *up to this point* semantic as the remaining `<displayed/>`. However in the review phase it was concluded that **most implementers prefer the per-message precision of Message Delivery Receipts (XEP-0184) for received tracking**. While `<displayed/>` has been widely implemented during a 10+ year review phase there was seemingly **no demand for `<acknowledged/>`**."

— https://xmpp.org/extensions/xep-0333.html §11

**Means today:** the ecosystem converged on **per-message for delivered, up-to-cursor for read**. Don't build a three-tier marker system; build the split that survived 10 years of review.

## 1. Transport

**Recommendation: WebSocket over TLS on 443, length-delimited protobuf frames, app-level ping every 30–45 s.** Raw TCP buys nothing a WSS frame can't carry while forfeiting SNI multiplexing, L7 routing, and the supported Ingress path. gRPC adds HTTP/2 semantics and proxy sensitivity you don't need for a single bidirectional stream. QUIC requires UDP/443 plus a TCP fallback anyway — you'd build two transports; defer to v2.

**Documented facts this rests on:**

| Layer | Fact | Source |
|---|---|---|
| **nginx** | "By default, the connection will be closed if the proxied server does not transmit any data within **60 seconds**. This timeout can be increased with the `proxy_read_timeout` directive. Alternatively, the proxied server can be configured to periodically send WebSocket ping frames to reset the timeout." Also: `Upgrade` is hop-by-hop, so you must `proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection $connection_upgrade;` | https://nginx.org/en/docs/http/websocket.html |
| **Azure Standard LB** | "idle timeout range of **4 minutes to 100 minutes**… **The default setting is 4 minutes for all rule types.** If a period of inactivity exceeds the timeout value, the TCP or HTTP session… isn't guaranteed to be maintained." Outbound rules: 4–120 min. `--idle-timeout` + `--enable-tcp-reset` | https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-tcp-idle-timeout |
| **AKS** | "The Azure Load Balancer operates at **layer 4**." Standard SKU default; Basic retired 2025-09-30 | https://learn.microsoft.com/en-us/azure/aks/load-balancer-standard |
| **ingress-nginx raw TCP** | "the Kubernetes Ingress resource **only officially supports routing external HTTP(s) traffic**"; needs `--tcp-services-configmap` keyed `<external port>:<namespace/service name>:<service port/name>:[PROXY]:[PROXY]`, **and** the port must also be added to the ingress-nginx `Service` spec | https://kubernetes.github.io/ingress-nginx/user-guide/exposing-tcp-udp-services/ |

**Cost of raw TCP, concretely:** one port ≈ one service (no SNI), no path/host routing, ConfigMap edit + Service edit for every change, off the supported Ingress path. **The 4-minute Azure LB default is the single most likely cause of unexplained production disconnects.**

**Settings to apply:** LB `--idle-timeout 30 --enable-tcp-reset true`; nginx `proxy_read_timeout 120s`; client ping 30–45 s (comfortably inside every timer). TCP reset converts silent black-holes into fast deterministic reconnects.

⚠️ **UNVERIFIED:** the AKS annotation for LB idle timeout. I inferred **`service.beta.kubernetes.io/azure-load-balancer-tcp-idle-timeout`** but did not fetch the canonical list. Confirm at https://cloud-provider-azure.sigs.k8s.io/topics/loadbalancer/#loadbalancer-annotations before writing manifests.

**Protocol semantics worth stealing from MQTT 5 without its transport:** a `Session Present` boolean telling the client whether server-side queue state survived [MQTT-3.2.2-3]; a negotiated `Session Expiry Interval` (property 0x11); and a "session taken over" close — "the Server sends a DISCONNECT packet to the existing Client with Reason Code of **0x8E (Session taken over)**… and MUST close the Network Connection of the existing Client [MQTT-3.1.4-3]" — https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html

**Frame envelope — copy Signal's field set:**
```protobuf
message Envelope {
  optional uint64 client_timestamp = 5;
  optional uint64 server_timestamp = 10;
  optional bool   ephemeral = 12;  // "should not be persisted if the recipient is offline"
  optional bool   urgent = 14 [default=true];
  optional bytes  server_guid = 21; // 16-byte UUID
}
```
— `signalapp/Signal-Server:service/src/main/proto/TextSecure.proto:12-45`. `ephemeral` and `urgent` as wire flags are cheap and high-value (typing indicators shouldn't store-and-forward; not everything deserves a push).

## 2. Message IDs and Ordering

### Matrix `txn_id` — client-generated, idempotency-only

> "The purpose of the transaction ID is to allow the homeserver to distinguish a new request from a retransmission of a previous request so that it can make the request **idempotent**. The transaction ID should **only** be used for this purpose."
> "It is recommended that clients use either **version 4 UUIDs or a concatenation of the current timestamp and a monotonically increasing integer**."
> "Where a retransmission has been identified, the homeserver should **return the same HTTP response code and content** as the original request… would return a `200 OK` with the `event_id` of the original request."
> "The scope of a transaction ID is for a single **device**, and a single **HTTP endpoint**."

Two traps: same txn_id on two endpoints = two distinct requests; and **token refresh does not reset scope** — "if a client re-uses a transaction ID for the same endpoint after refreshing an access token, it will be assumed to be a duplicate request and ignored." Logout/login *does* (new device).

— `matrix-org/matrix-spec:content/client-server-api/_index.md:305-350`

### `insert_item.lua` — the whole pattern in 24 lines

This is Signal's entire per-device enqueue, executed atomically on the Redis slot owning that device's keys:

```lua
local queueKey         = KEYS[1] -- sorted set of Envelopes for a device, by queue-local ID
local queueMetadataKey = KEYS[2] -- hash of message GUID to queue-local IDs
local eventChannelKey  = KEYS[3] -- pub/sub channel for message availability events

if redis.call("HEXISTS", queueMetadataKey, guid) == 1 then
    return tonumber(redis.call("HGET", queueMetadataKey, guid))   -- idempotent replay
end

local messageId = redis.call("HINCRBY", queueMetadataKey, "counter", 1)  -- monotonic seq
redis.call("ZADD", queueKey, "NX", messageId, message)
redis.call("HSET", queueMetadataKey, guid, messageId)
redis.call("EXPIRE", queueKey,         3974400) -- 46 days
redis.call("EXPIRE", queueMetadataKey, 3974400)
return redis.call("SPUBLISH", eventChannelKey, eventPayload) > 0
```
— https://github.com/signalapp/Signal-Server/blob/main/service/src/main/resources/lua/insert_item.lua

**Five properties from one script:** idempotent insert (GUID→existing ID, *returns the original ID* — same contract as Matrix's "same response"); per-recipient monotonic sequence (`HINCRBY`); ordered storage (sorted set scored by that sequence); retention (46-day TTL); and wake-up (`SPUBLISH`). **Ordering is solved by making the queue single-writer — the Redis slot is the writer, not any server instance.** No vector clocks, no Lamport timestamps.

### Client-side correlation

matrix-rust-sdk keys its outbox on the txn_id and surfaces the swap as a typed event:
```rust
SentEvent { transaction_id: OwnedTransactionId, event_id: OwnedEventId },
```
— `matrix-org/matrix-rust-sdk:crates/matrix-sdk/src/send_queue/mod.rs:2924-2931`

⚠️ **UNVERIFIED:** Slack `client_msg_id` — not researched. See https://api.slack.com/events/message.
⚠️ **PARTIAL:** RFC 9562 — I captured §6.3 (generator state: keep last timestamp/counter in stable storage for "monotonic error checking with UUIDv6 and UUIDv7"; batch-allocate timestamps if shared state is costly) but **not** the §5.7 v7 bit layout. Confirm at https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7

### Multi-instance ordering — the three real options

| Strategy | Used by | Mechanism |
|---|---|---|
| **Single-writer per queue** | Signal | Atomic script on the recipient's shard; counter is per-recipient |
| Consistent hashing on conversation key | Discord | "we provide a routing key. For messages, this is a channel ID, so all requests for the same channel go to the same instance" — https://discord.com/blog/how-discord-stores-trillions-of-messages |
| Totally-ordered queue, independent cursors | Meta (Iris) | See §3 |

**Recommendation:** client mints **UUIDv7 `client_msg_id` once**, at send, persisted to the local outbox *before* any network attempt — it is the outbox PK and never changes across retries or restarts. Server treats it as idempotency key against `UNIQUE (recipient_id, client_msg_id)`; on collision return the *existing* `seq`. Server assigns `seq BIGINT` from a **per-recipient** counter (not global) — that makes the inbox single-writer and ordering a plain `ORDER BY seq`. Ack frame carries `{client_msg_id, server_msg_id, seq, server_timestamp}`. UUIDv7's time-ordered prefix keeps the index B-tree-friendly where UUIDv4 would fragment it.

## 3. Server-Side Inbox / Store-and-Forward

### Signal-Server: two tiers

**Hot:** Redis sorted set per device, scored by the queue-local counter, 46-day TTL (`insert_item.lua`, above).

**Cold:** a background drainer persists to DynamoDB in bounded batches:
```java
public class MessagePersister implements Managed {
  private final MessagesCache messagesCache;
  private final MessagesManager messagesManager;
  private final Duration persistDelay;
  static final int QUEUE_BATCH_LIMIT = 100;
  static final int MESSAGE_BATCH_LIMIT = 100;
  ...Retry.backoff(3, Duration.ofSeconds(1))
```
— `signalapp/Signal-Server:service/src/main/java/org/whispersystems/textsecuregcm/storage/MessagePersister.java:45-110`

DynamoDB evidenced by the `ItemCollectionSizeLimitExceededException` import (`:43`); a parallel FoundationDB path is mid-migration (`ClearExpiredFoundationDbMessagesCommand`, `TrimOversizedFoundationDbMessageQueuesCommand`).

### Meta Iris: ordered queue, independent pointers

> "Iris is a **totally ordered queue** of messaging updates (new messages, state change for messages read, etc.) with **separate pointers** into the queue indicating the last update sent to your Messenger app and the traditional storage tier. When successfully sending a message to disk or to your phone, the corresponding pointer is advanced. **When your phone is offline, or there is a disk outage, the pointer stays in place while new messages can still be enqueued and other pointers advanced.**"

Recency tiers: most-recent from Iris memory → **a week's worth** from the queue's backing store → older history from the traditional disk tier. Backing store = MySQL + flash, semi-sync replication, <30 s hardware-failure handling.
— https://engineering.fb.com/2014/10/09/production-engineering/building-mobile-first-infrastructure-for-messenger/

**The shape to copy: one ordered log per user, N independent cursors over it.** Delivery speed decouples from storage speed.

### XEP-0198 Stream Management (h-counters)

Stream-level, not end-to-end. `<r/>` requests an ack, `<a h='N'/>` answers with the count of **handled** stanzas; `h` starts at 0 when SM is enabled and increments by one per stanza handled; wraps at 2³². "Handled" is defined as the server **accepting responsibility** — "until a stanza has been affirmed as handled by the server, that stanza is the responsibility of the sender (e.g. to resend it or generate an error)." Resumption exchanges last-received sequence numbers so both sides know exactly what to retransmit. On unresumed streams the server SHOULD treat unacked stanzas as if sent to an unavailable resource — error, alternate resource, or **offline storage**. The spec is honest that replay produces duplicates: "there is no way to prevent such a result in this protocol, although use of the XMPP 'id' attribute… can at least assist the intended recipients in weeding out duplicate stanzas." That is precisely why §2's idempotency key is mandatory. — https://xmpp.org/extensions/xep-0198.html

### XEP-0313 MAM (archive)

Server-side archive queryable per bare JID (user) or room JID (MUC). Each stored message carries "a server-assigned UID that MUST be **unpredictable and unique** within the archive", communicated to the recipient via an XEP-0359 `<stanza-id/>` element with `by` set to the archive address. Ordering rule: "Order within the archive MUST be preserved… implementors should take care **not to rely on timestamps alone** for ordering messages, as multiple messages may share the same timestamp." Deletion rule: "Any such deleted messages MUST be the oldest in the archive, i.e. it is **not permitted to create gaps or 'holes'**… The UIDs of deleted messages MUST NOT be reused." — https://xmpp.org/extensions/xep-0313.html

(Matrix's sliding sync adds a useful escape hatch: "**Servers should not need to store all past since tokens.** If a since token has been discarded we should gracefully degrade to initial sync," with HTTP 400 `M_UNKNOWN_POS` as the signal — https://github.com/matrix-org/matrix-spec-proposals/blob/erikj/sss/proposals/4186-simplified-sliding-sync.md)

### Recommendation: Postgres inbox + per-device cursor + Redis as signal-only backplane

```sql
CREATE TABLE inbox (
  recipient_id    UUID    NOT NULL,
  seq             BIGINT  NOT NULL,          -- per-recipient monotonic, NOT global
  client_msg_id   UUID    NOT NULL,          -- UUIDv7 idempotency key
  sender_id       UUID    NOT NULL,
  conversation_id UUID    NOT NULL,
  payload         BYTEA   NOT NULL,
  server_ts       TIMESTAMPTZ NOT NULL DEFAULT now(),
  ephemeral       BOOLEAN NOT NULL DEFAULT false,
  expires_at      TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (recipient_id, seq)
);
CREATE UNIQUE INDEX inbox_idem ON inbox (recipient_id, client_msg_id);

CREATE TABLE device_cursor (
  device_id    UUID   NOT NULL,
  recipient_id UUID   NOT NULL,
  acked_seq    BIGINT NOT NULL DEFAULT 0,
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (device_id, recipient_id)
);

CREATE TABLE recipient_seq (            -- the single-writer counter
  recipient_id UUID PRIMARY KEY,
  next_seq     BIGINT NOT NULL DEFAULT 1
);
```

**Enqueue** (one transaction, mirroring `insert_item.lua`): `INSERT … ON CONFLICT (recipient_id, client_msg_id) DO NOTHING RETURNING seq`; if no row returned, `SELECT seq` for the existing key and return *that* — same contract as Matrix's "return the same response." Allocate `seq` via `UPDATE recipient_seq SET next_seq = next_seq + 1 … RETURNING next_seq - 1`, which row-locks per recipient and gives you single-writer ordering without a global lock.

**Drain:** `SELECT … WHERE recipient_id=$1 AND seq > $2 ORDER BY seq LIMIT 100`.

**Ack semantics:** client acks a `seq`; server does `UPDATE device_cursor SET acked_seq = GREATEST(acked_seq, $seq)` — **monotonic-forward-only**, never rewind. Rows are deleted only by a retention sweep (Signal: 46 days) honouring MAM's oldest-first, no-holes, no-UID-reuse rules. Multiple devices = multiple cursors over one log (Iris's pointer model).

**Redis's only job: wake-ups.** After the transaction **commits**, `PUBLISH notify:{device_id}` with a tiny payload. The holding gateway drains `WHERE seq > cursor`. **If the pub/sub message is lost, nothing is lost** — the next drain or reconnect picks it up. Never put the message body on pub/sub.

**Trade-off accepted:** single Postgres is a write bottleneck and one failure domain; you will eventually partition by `recipient_id`. That's a known, deferred, optional migration — and Meta ran Messenger on MySQL+flash. Starting on Kafka/Cassandra costs you immediately and permanently.

## 4. Delivery Receipts

### The three specs on the wire

**XEP-0184 — per-message, two elements in `urn:xmpp:receipts`.** Sender attaches `<request/>` to the content message; recipient returns an ack message containing `<received id='…'/>`. Honest about its limits: "this protocol does not provide complete or even partial reliability or guaranteed delivery. Therefore, the sender SHOULD NOT impute any meaning to the fact that it has not received an ack message." Multi-device reality: "the sender of the content message needs to be prepared to **receive multiple ack messages**." Anti-loop: "an entity MUST NOT include a receipt request in an ack message." Archive rule: "An entity MUST NOT send an ack message when a user views messages that have been **archived**." And the group warning: "It is **NOT RECOMMENDED** to request a receipt when sending a content message of type 'groupchat'… because **the sender would receive one ack message from each occupant of the room**, thus significantly increasing the number of stanzas sent through the room." — https://xmpp.org/extensions/xep-0184.html

**XEP-0333 — up-to marker, `<markable/>` request + `<displayed id='…'/>` response in `urn:xmpp:chat-markers:0`.** "Displayed Markers carry a semantic of *all messages up to this point*." Explicitly heuristic: "Displayed Markers do not mark each individual message, nor do they assume a reliable transport… can only provide a heuristic solution, but this is often satisfactory for the majority of use cases." Rules: markers **only move forward** (older refs "MUST be ignored"); only send for the most recent message when several are displayed at once; never respond to a marker with a marker; never send markers for your own messages received via Carbons/MAM. In MUCs the sender-chosen `id` is spoofable, so "clients MUST always use the MUC-assigned id" from XEP-0359, and `<stanza-id/>` from a MUC that doesn't announce XEP-0359 support "should be considered spoofed and MUST be ignored." Privacy: "Clients SHOULD provide ways to opt-out"; "a sender SHOULD NOT send Displayed Markers to recipients who are not otherwise authorized to view its presence." **Narrowing/rename detailed in §0.3.** — https://xmpp.org/extensions/xep-0333.html

**Matrix `m.receipt` — up-to markers, batched, with a private variant.** "Sending a receipt for each event can result in sending large amounts of traffic… receipts are implemented using **'up to' markers**." Trigger condition: "Clients should send read receipts when there is some certainty that the event in question has been **displayed**… Simply receiving an event does not provide enough certainty. The user SHOULD need to *take some action*… Clients SHOULD NOT send read receipts for events sent by their own user." Fanout control: "receipts SHOULD be **batched into one event per room and thread** before delivering them to clients," delivered as deltas under `ephemeral`. Privacy solved structurally with `m.read.private` (v1.4): "Servers **MUST NOT** send the `m.read.private` receipt to any other user than the one which originally sent it" — and it's excluded from federation EDUs. Caveat: "receipts are sent outside the context of the event graph, there are **no integrity checks**." — `matrix-org/matrix-spec:content/client-server-api/modules/receipts.md:1-120, 180-215`

### Who emits each transition

| Transition | Emitter | Reaches sender via | Pitfall |
|---|---|---|---|
| `pending → sent` | **Server**, after the inbox row **commits** | Direct ack on sender's own socket, carrying `{client_msg_id, server_msg_id, seq}` | Ack before commit = silent message loss |
| `sent → delivered` | **Server** (Signal) or recipient client (XMPP) | Server-generated envelope routed to sender's inbox | XMPP model: N devices ⇒ N receipts |
| `delivered → read` | **Recipient client**, on actual display | Up-to cursor, batched per conversation | Receipt storms; privacy; archive replay |

**Signal makes "delivered" a server concern** — `SERVER_DELIVERY_RECEIPT = 5` is an `Envelope.Type` (`signalapp/Signal-Server:service/src/main/proto/TextSecure.proto:19`), alongside `PLAINTEXT_CONTENT = 8; // for decryption error receipts`. This is strictly better for you: no recipient-side cooperation needed, no new trust assumption, and it's free — you already have the per-device ack that advances the cursor.

### Group fanout — the ACS datapoint

> "Read receipts and typing indicators **aren't supported on chat threads with more than 20 participants**."

— https://learn.microsoft.com/en-us/azure/communication-services/concepts/service-limits

A major cloud vendor shipped a **hard cutoff at 20** rather than solve group read-state fanout. Combined with XEP-0184's explicit N²-per-room warning, that's two independent sources saying per-member group receipts don't scale.

**Receipt strategy for your design:**
1. **Delivered** — per-message, **server-generated**, free given your cursor mechanism.
2. **Read** — client-generated, **up-to-cursor, monotonic-forward-only**, batched per conversation. Ignore anything that moves backwards (XEP-0333 rule).
3. **Private read cursor from day one** — Matrix's `m.read.private` split. It clears your own unread count without fanout. Retrofitting is painful because it changes the fanout path.
4. **Groups:** aggregate to a single `min(read_seq)` across members for one "all read" indicator rather than per-member ticks; degrade or disable per-member read state above a participant threshold, following ACS's precedent.
5. Accept that read state is a heuristic, never per-message truth. You can answer "Bob has read up to seq N", not "which messages did Bob read."

## 5. Multi-Instance Connection Routing

### Recommendation: pub/sub backplane carrying a wake-up signal only

| Approach | Finds B's instance by | Failure mode | Verdict |
|---|---|---|---|
| **Pub/sub (signal-only)** | Broadcast on `notify:{device_id}`; holder reacts | Lost pubsub = **delay only** (queue is truth); duplicates harmless | ✅ **Recommended** |
| Registry (`user→instance`) + direct forward | Lookup then RPC | **Stale entry silently blackholes messages**; needs TTL+heartbeat; split-brain on partition | ⚠️ Worse failure mode |
| Consistent hashing | Deterministic from user ID | Rebalance on every scale event; hot-key stampede | ⚠️ Premature |
| Pub/sub carrying the payload | Broadcast body | **Lost pubsub = lost message** | ❌ Never |

### Signal's implementation — the authoritative paragraph

> "The Redis message availability manager distributes events related to client presence and message availability to registered listeners… Clients are considered 'present' if they have an open WebSocket connection… Redis message availability managers ensure that clients have **at most one active message delivery channel at a time on a best-effort basis**."
> "@implNote The Redis message availability manager uses the **Redis 7 sharded pub/sub** system to distribute events. This system makes a best effort to ensure that a given client has only a single open connection across the fleet of servers, but **cannot guarantee at-most-one behavior**."

— `signalapp/Signal-Server:service/src/main/java/org/whispersystems/textsecuregcm/push/RedisMessageAvailabilityManager.java:40-56`

Mechanics: routing key is **`record AccountAndDeviceIdentifier(UUID accountIdentifier, byte deviceId)`** — device, not user (`:85`). Each instance has `private final UUID serverId = UUID.randomUUID()` and broadcasts a `ClientConnectedEvent{serverId}` on connect, which "displaces immediately" any prior presence and fires `handleConflictingMessageConsumer()` on the displaced listener (`:88-95, :128-133`). Resharding is handled: `pubSubConnection.subscribeToClusterTopologyChangedEvents(this::resubscribe)` (`:110`) — a failure mode most designs forget.

### Discord: reconnect storms, documented

**The ring became the bottleneck** (2017 Elixir post):
> "as Discord scaled, we started to notice issues when we had **bursts of users reconnecting**. The Erlang process responsible for controlling the ring would start to get so busy that it would fail to keep up with requests… and the whole system would become overloaded."
> "If the session server were to crash and restart, it would take about **30 seconds** just for the cost of lookups on the ring."

Fix path: C-port ring → ETS (7 µs reads, 17.5 s total) → `FastGlobal`/mochiglobal read-only shared heap (**0.3 µs**, **750 ms** total) at the cost of ~1 s to rebuild the module on ring change.

**Then the next failure — a genuine thundering herd:**
> "nearly **5,000,000 session processes were trying to stampede ten of these processes** (one on each guild node)… the call… would timeout and leave the request in the queue of the guild registry. It would then retry the request after a backoff, but **perpetually pile up requests and get into an unrecoverable state**. Sessions would block on these requests until they timed out while receiving messages from other services, causing them to **balloon their message queues and eventually OOM the whole Erlang VM resulting in cascading service outages.**"

The fix was a **semaphore** (bounded concurrency, fast-fail), explicitly *not* a circuit breaker: "we didn't want a burst in timeouts to result in a temporary state where no attempts are made at all." Fanout was separately sharded via Manifold: "Manifold distributes the work of sending messages to the remote nodes of the PIDs, which guarantees that the sending processes at most only calls `send/2` equal to the number of involved remote nodes."
— https://discord.com/blog/how-discord-scaled-elixir-to-5-000-000-concurrent-users

**Mitigations baked into Discord's wire protocol** (official docs):
- **Jitter:** "wait `heartbeat_interval * jitter` where `jitter` is any random value between 0 and 1… meant to **prevent too many clients from reconnecting their sessions at the exact same time (which could cause an influx of traffic)**."
- **Resume token:** cache `session_id` + the latest non-null `s` (sequence); "The Ready event contains a `resume_gateway_url`" — resume goes **back to the instance holding state**.
- **Asymmetric rate limits:** "Clients are limited to 1000 `IDENTIFY` calls… in a 24-hour period… **but does not include `RESUME` calls.**" Exceeding it: "all active sessions for the app will be terminated, the bot token will be reset."
- **Zombie detection:** "If a client does not receive a heartbeat ACK between its attempts at sending heartbeats… terminate the connection with any close code **besides `1000` or `1001`**, then reconnect and attempt to Resume." (Close code choice is the resume-vs-reidentify signal.)
— https://docs.discord.com/developers/events/gateway

⚠️ **UNVERIFIED:** I found **no** primary Discord post on a "sessions service" or a 2023–24 reconnect-storm retrospective; searches returned SEO content only. Everything above is from the 2017 post + official docs, both primary.

### Design

Route on **`(user_id, device_id)`**. Write inbox row → **commit** → `PUBLISH notify:{device_id}`. Gateways subscribe only to keys for devices they currently hold. Broadcast `ClientConnected{server_id}` to displace stale connections (best-effort, as Signal does). Protocol: jittered first heartbeat, client-echoed `seq`, cheap `RESUME` vs rate-limited `IDENTIFY`, bounded-concurrency fast-fail (semaphore) on any shared lookup in the connect path. **Staggered deploys:** `preStop` hook closes a *fraction* of connections at a time with a "reconnect with backoff" close frame; `terminationGracePeriodSeconds` longer than that drain. Start on plain Redis `PUBLISH`; the upgrade to Redis 7 `SPUBLISH` is a one-line change when you shard.

**Trade-off accepted:** Redis becomes a shared dependency and pub/sub is at-most-once — worst case a message waits for the next drain tick. Correct failure mode for a messenger (late, never lost), and strictly better than a registry whose stale entries blackhole silently.

## 6. Auth

### Opaque vs JWT for a long-lived socket gateway

| Token style | Gateway validation | Revocation latency | Fit for a stateful WS gateway |
|---|---|---|---|
| **Opaque + central introspection** | **Network RTT to auth-service on every connect** | Immediate | ❌ Puts a synchronous external dependency in the exact code path that gets hammered during a reconnect storm |
| **Short-lived signed JWT (5–15 min) + refresh token** | Local signature verify against cached JWKS; zero network | Bounded by TTL (≤15 min) | ✅ **Recommended** |
| Long-lived JWT (hours/days) | Local | ❌ Effectively none | ❌ |
| JWT + Redis `jti` revocation set | Local verify + one Redis `SISMEMBER` | Immediate | ✅ v2 upgrade; keeps hot path in-cluster |

**Recommendation: EdDSA/Ed25519-signed JWTs, 5–15 min TTL, long-lived refresh tokens, JWKS cached by the gateway.** Claims: `sub`, `device_id`, `email_verified`, `exp`, `jti`, and `aud` set to the gateway's **actual URL** — RFC 9700: "To prevent phishing, it is necessary to use the actual URL the client will send requests to"; structured tokens also let the AS mint per-resource content, which has "huge functional and privacy advantages in deployments using structured access tokens" (https://www.rfc-editor.org/rfc/rfc9700.html#section-4.10.2).

**Reasoning tied to §5:** the documented Discord failure was 5M session processes stampeding ten shared processes, where "the call… would timeout and leave the request in the queue… It would then retry the request after a backoff, but perpetually pile up requests and get into an unrecoverable state… eventually OOM the whole Erlang VM resulting in cascading service outages" (https://discord.com/blog/how-discord-scaled-elixir-to-5-000-000-concurrent-users). Opaque-token introspection makes auth-service exactly that shared chokepoint — every reconnecting client issues a blocking call to it, during the one moment the fleet is already degraded. Local JWT verification makes connect-path auth **O(1) CPU, zero network**, so a reconnect storm is bounded by your own capacity rather than by a third service's queue depth. Apply the same semaphore pattern Discord landed on (bounded concurrency, fast-fail — explicitly *not* a circuit breaker, because "we didn't want a burst in timeouts to result in a temporary state where no attempts are made at all") to any remaining shared lookup in the connect path.

### Token expiry mid-connection: re-auth frame, not forced disconnect

**Design:** validate once at connect; the *connection* is thereafter the security context — do not re-validate per frame. ~60 s before `exp`, server sends `AuthExpiring`; client refreshes out-of-band and sends `ReAuth{token}`; gateway swaps the context in place. Only if no valid `ReAuth` arrives by `exp + grace` do you close, with a **distinct close code meaning "re-auth required"** so clients don't blind-retry into a loop.

**Prior art actually verified:**

| Source | What it establishes | Citation |
|---|---|---|
| **MQTT 5** | A dedicated `AUTH` packet type exists specifically for re-authentication on an established connection; `0x8C (Bad authentication method)` is the paired failure code — i.e. the protocol designers treated mid-connection re-auth as a first-class case, not a disconnect | https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html §3.1.4 |
| **Matrix** | Token refresh must **not** break in-flight idempotency: "if a client re-uses a transaction ID for the same endpoint after **refreshing** an access token, it will be assumed to be a duplicate request and ignored" — refresh is explicitly a non-event for request scope | `matrix-org/matrix-spec:content/client-server-api/_index.md:341-345` |
| **Discord** | Resume must be cheap, identify expensive: "Clients are limited to 1000 `IDENTIFY` calls… in a 24-hour period… **but does not include `RESUME` calls**"; breaching it means "all active sessions for the app will be terminated, the bot token will be reset" | https://docs.discord.com/developers/events/gateway |

Forcing a disconnect on every expiry converts a routine, *clock-synchronised* event into a fleet-wide simultaneous reconnect — manufacturing the §5 storm on a timer.

### OWASP Argon2id — exact current configurations

> "**Use Argon2id with a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism.**"

Two sanctioned parameter sets:
- **m=19456 (19 MiB), t=2, p=1**
- **m=47104 (46 MiB), t=1, p=1** — "(Do not use with Argon2i)"

Fallbacks, verbatim: scrypt "minimum CPU/memory cost parameter of (2^17), a minimum block size of 8 (1024 bytes), and a parallelization parameter of 1"; legacy bcrypt "work factor of 10 or more and with a password limit of **72 bytes**"; FIPS-140 "PBKDF2 with a work factor of **600,000 or more**… HMAC-SHA-256."

Two rules implementers get wrong: "**Parallelism controls the number of lanes over which the memory is divided; increasing p does not multiply the total memory or act as an iteration count**," and "As a general rule, calculating a hash should take **less than one second**." Pepper caveat: "Peppers cannot be changed without knowledge of a user's password. Therefore changing a pepper will require forcing all users whose passwords were protected by the previous pepper to reset their passwords."

— https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html

**Use m=19456, t=2, p=1**, calibrated to ~250 ms on your actual AKS node SKU, parameters embedded in the PHC-format hash string so you can raise them on next successful login.

### Email verification: signed single-use link vs 6-digit code

OWASP is explicit on the default: "**Use URL tokens for the simplest and fastest implementation.**" Token requirements, verbatim: "Randomly generated using a cryptographically safe algorithm / Sufficiently long to protect against brute-force attacks / Stored securely / **Single use and expire after an appropriate period**." PINs, if chosen instead, are "numbers (between **6 and 12 digits**)" and you "**Create a limited session from that PIN** that only permits the user to reset their password."

| | Signed single-use link | 6-digit code |
|---|---|---|
| Brute-force surface | Negligible (≥128-bit) | 10⁶ — **requires attempt counting** |
| Cross-device UX | Breaks (link opens on wrong device) | Works |
| Leak vector | Referrer, mail-scanner prefetch | Shoulder-surf |
| OWASP default | ✅ "simplest and fastest" | Offered as alternative |

**Mandatory hardening (all verbatim OWASP):**
- "Return a **consistent message** for both existent and non-existent accounts" **and** "Ensure that the time taken for the user response message is **uniform**" — the enumeration pitfall is *two*-sided: content **and** timing. "This could be achieved by using asynchronous calls or by making sure that the same logic is followed, instead of using a quick exit method."
- "Implement protections against excessive automated submissions such as **rate-limiting on a per-account basis**, requiring a CAPTCHA… Otherwise an attacker could make **thousands of password reset requests per hour** for a given account, flooding the user's intake system… with useless requests."
- "**Don't rely on the `Host` header** while creating the reset URLs to avoid Host Header Injection attacks. The URL should either be hard-coded, or validated against a list of trusted domains."
- "adds the **`Referrer Policy`** tag with the **`no-referrer`** value in order to avoid referrer leakage."
- "**Do not make a change to the account until a valid token is presented**, such as locking out the account."

**On attempt-count lockout — OWASP recommends against locking the account:**
> "Accounts should **not** be locked out in response to a forgotten password attack, as this can be used to **deny access to users with known usernames**."

So: rate-limit and invalidate the *token*, never the *account*.

— https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html

⚠️ **UNVERIFIED (my recommendation, not primary-sourced):** OWASP says "expire after an appropriate period" without a number. I suggest **link: 15–30 min; code: 10 min, max 5 attempts then invalidate the code (not the account) and require a fresh request; per-account 3/hour, per-IP 10/hour**. These are engineering judgment. If you need a citable number, check NIST SP 800-63B (https://pages.nist.gov/800-63-4/sp800-63b/) — referenced by the OWASP sheet but not fetched in this research.

**Operational tie-in:** the rate limit is load-bearing against §0's provider send caps. An unthrottled verification endpoint exhausts any provider's hourly quota in seconds.

### Device identity and binding to the session

§5 routes on `(user_id, device_id)`, so `device_id` must be server-issued, stable across reconnects, and revocable.

**Verified prior art:**
- **Signal** uses `record AccountAndDeviceIdentifier(UUID accountIdentifier, **byte** deviceId)` — `signalapp/Signal-Server:.../push/RedisMessageAvailabilityManager.java:85`. Note the type: a **`byte`**, so ≤128 devices per account by construction. Device identity is a small server-assigned ordinal, not a client-chosen string.
- **Matrix** binds device creation to login: "if a client logs out and back in between two requests using the same transaction ID, the requests are distinct because **the act of logging in and out creates a new device (unless an existing `device_id` is given during the login process)**" — `matrix-org/matrix-spec:content/client-server-api/_index.md:336-341`. So: server mints a `device_id` at first login; the client may *present* a prior `device_id` to reclaim it.
- **Discord** issues the session handle server-side in `READY` and pairs it with a `resume_gateway_url` so resume returns to the instance holding state — https://docs.discord.com/developers/events/gateway.

**Recommendation:** auth-service mints `device_id` (UUID) on first login for a given client install; the client persists it next to the refresh token and presents it on subsequent logins to reclaim the same ID. `device_id` is a **JWT claim**, so the gateway learns it from the validated token — never from a client-supplied frame field. On connect, the gateway subscribes to `notify:{device_id}` and broadcasts `ClientConnected{server_id}` to displace any stale holder (§5). Logout, refresh-token revocation, and device deletion all converge on: drop the `device_cursor` row, revoke the refresh token, close the socket with the re-auth close code. Cap devices per account (Signal's `byte` is a reasonable prior); each device gets its own cursor over the shared inbox log, per Iris's pointer model.

### matrix-rust-sdk send queue — real semantics

Semantics: strict FIFO per conversation ordered `(priority DESC, enqueued_at ASC)`; a row with non-NULL `wedged_reason` blocks **its conversation and nothing else**; exponential backoff with jitter (~1 s → cap ~60 s) on recoverable errors, then disable that conversation's queue and emit `SendError{is_recoverable:true}` rather than spinning; terminal errors set `wedged_reason` and emit `is_recoverable:false`. **Delete a row only on the server ack matching its `client_msg_id`** — making the outbox exactly the set of messages in state `pending`. Scan and respawn drain tasks inside `Client::new()`, before returning, rather than leaving it to integrators.

Storage is a compile-time feature in matrix-rust-sdk, not a hard dependency: `bundled-sqlite` (default; statically compiled, so no system-library skew across Android/iOS/desktop) vs `indexeddb` for web — `bindings/matrix-sdk-ffi/Cargo.toml:25-31`. **No evidence** of sled or redb in any surveyed messenger SDK.

### libsignal's packaging model

> "libsignal contains platform-agnostic APIs used by the official Signal clients and servers, exposed as a **Java, Swift, or TypeScript** library. The underlying implementations are written in **Rust**."
> "the products of this repository are the Java, Swift, and TypeScript libraries that wrap the underlying Rust implementations. All APIs and implementations are subject to change without notice, as are the **JNI, C, and Node add-on 'bridge' layers**."
> "**Use outside of Signal is unsupported.**"

— `signalapp/libsignal:README.md:1-30`

So: **Rust core → hand-written JNI (Java) + C ABI (Swift) + Node add-on / N-API (TypeScript)**. No UniFFI; three bridges, three maintenance burdens. libsignal is the **crypto/protocol core only** — it contains no outbox, no transport, no queue.

Contrast matrix-rust-sdk, which uses **UniFFI** from one crate to all targets:
```toml
[lib]
crate-type = ["cdylib",    # uniffi → Android
              "staticlib", # uniffi → iOS
              "lib"]       # uniffi → JS/Wasm
```
plus per-target async shims — `uniffi = { features = ["tokio"] }` on native, `uniffi = { features = ["wasm-unstable-single-threaded"] }` on wasm — `bindings/matrix-sdk-ffi/Cargo.toml:12-20, 112-121`.

**Both reference projects put the logic in Rust and bind out. That question is settled; only the generator differs.** Your napi-rs + cbindgen split is libsignal's shape minus JNI — legitimate, and lighter than three hand-written bridges, but note it gives you a C *header*, not a binding: you still hand-write the Swift/Kotlin wrapper over it, and every call crosses `unsafe`. If Kotlin *and* Swift *and* Python are on the roadmap, UniFFI pays for itself — that's the matrix the matrix-rust-sdk team optimised for.

### Core vs bindings split

| Layer | Contents |
|---|---|
| **Rust core** (no FFI types anywhere) | Wire codec; connection state machine (connect → auth → identify/resume → heartbeat → drain); **send queue** with ordering/wedging/backoff; SQLite outbox + message cache; cursor and ack bookkeeping; retry policy; `SendQueueUpdate` as a native `tokio::sync::broadcast` channel |
| **napi-rs binding** | Type marshalling; `AsyncTask`/`Promise` adaptation; `ThreadsafeFunction` for the event stream → `EventEmitter`; Node-side path/keychain resolution |
| **cbindgen / C ABI binding** | `extern "C"` shims; opaque handle types; a registered callback + context pointer for events; explicit `*_free` for every returned allocation |
| **Neither** | Any decision-making. The instant binding code branches on business logic, you've forked behaviour N ways. |

**Public surface — three things:** `Client` (connect/auth/lifecycle, calls respawn-unsent internally), `ConversationSendQueue` with `send() -> SendHandle` exposing `abort()`/`retry()`/`unwedge()`, and one `SendQueueUpdate` stream mirroring matrix's enum including `is_recoverable: bool`. Preserve the wedging invariant verbatim so the UI cannot render out of order.

### Async and callbacks across each boundary

**napi-rs (TS/Node):** napi-rs owns no runtime — libuv does. Return `napi::bindgen_prelude::AsyncTask` or an `async fn` (napi-rs spawns onto its own pool) for request/response. For the **event stream**, create one `ThreadsafeFunction` at `Client` construction, hold it in the core's subscriber task, and call it from the tokio thread; TSFN is explicitly designed for cross-thread invocation into the JS thread. Do **not** poll from JS.

**cbindgen (C ABI):** no async exists in C. Expose `client_subscribe(handle, fn(*mut c_void, *const Event), ctx: *mut c_void)`; the core spawns a task that invokes the callback on a tokio worker. **Document the threading contract explicitly** — Swift/Kotlin callers must assume callbacks arrive off the main thread and hop themselves (`DispatchQueue.main.async` / `withContext(Dispatchers.Main)`). For request/response, prefer completion callbacks over blocking shims; a blocking `block_on` from a caller thread that is itself inside a runtime will deadlock.

### Known traps

⚠️ *This subsection is engineering judgment, not prior-art research — I did not survey FFI incident reports.*

| Trap | Mitigation |
|---|---|
| **Panic unwinding across FFI = UB** | Wrap **every** `extern "C"` entry point in `std::panic::catch_unwind` and convert to an error code. Set `panic = "abort"` in release if you prefer the blunt instrument. (matrix-sdk-ffi ships `log-panics` with backtraces — `bindings/matrix-sdk-ffi/Cargo.toml:57` — evidence this bites in practice.) napi-rs catches panics and throws, but only at *its* boundary; panics in detached tokio tasks still abort. |
| **Tokio runtime ownership** | The core must **own exactly one** multi-thread runtime, created at `Client::new()` and stored in the handle. Never create a runtime per call; never `block_on` inside a runtime thread. Note matrix-rust-sdk needs distinct feature flags per target (`tokio` vs `wasm-unstable-single-threaded`) — budget for a per-target runtime shim. Node already has libuv, so the Rust runtime must stay on its own threads and only touch JS via TSFN. |
| **String ownership / lifetimes** | Across C ABI: return `*mut c_char` from `CString::into_raw` and pair **every** getter with a `_free` that calls `CString::from_raw`. Never return a pointer into a Rust-owned buffer that the caller might outlive. Never free a Rust allocation with the C allocator. napi-rs handles this via owned `String`/`Buffer` — one more reason to keep C ABI surface minimal. |
| **Cancellation** | Dropping a JS Promise does **not** cancel the Rust future. Give `SendHandle::abort()` real teeth: hold a `CancellationToken` per queued request, check it at every await point, and make abort idempotent. Model the "too late to abort" race exactly as matrix does — once the request is in flight, abort must become a server-side compensating action, not a local delete (`send_queue/mod.rs:47-53`). |
| **Opaque handle lifetime** | Return `Box::into_raw(Box::new(Arc<Inner>))`; require an explicit `*_free`. Guard against double-free with a magic/generation field in debug builds. |
| **Blocking the event callback** | If the host callback blocks (JS doing sync work, Swift hopping to main and waiting), your subscriber task stalls and the broadcast channel lags. Use a bounded channel and document that lagged receivers drop — mirroring how matrix exposes `SendQueue::subscribe_errors` separately from per-room streams. |

| 1 | **Email provider** | **Not ACS — SES or Resend, behind an `EmailSender` trait** | ACS Email **retired eff. 2028-09-30**, announced 2026-09-23; onboarding restrictions from **2026-10-23**; Azure-managed domain **5/min, 10/hour, "Higher limits available: No"** (https://learn.microsoft.com/en-us/azure/communication-services/acs-retirement-and-breaking-changes-guide, https://learn.microsoft.com/en-us/azure/communication-services/concepts/service-limits) | Second cloud account + 2–4 week sender warm-up — far cheaper than migrating off a dying service. **Act within 12 days.** ⚠️ Non-ACS pricing UNVERIFIED (aggregator-sourced) |
| 2 | **Inbox storage shape** | **Relational per-recipient log, not a message log/Kafka** | Meta "opted to build the queue storage on top of **MySQL and flash**… latency for enqueueing is an order of magnitude less" after evaluating and rejecting existing queue tech (https://engineering.fb.com/2014/10/09/production-engineering/building-mobile-first-infrastructure-for-messenger/) | Single write bottleneck; partition by `recipient_id` later — deferred and optional |
| 3 | **Receipt model** | **Per-message delivered + up-to-cursor read; no third tier** | XEP-0333 narrowed/renamed to "Displayed Markers", `<received/>` and `<acknowledged/>` **removed**: "most implementers prefer the per-message precision of XEP-0184 for received tracking… seemingly no demand for `<acknowledged/>`" (https://xmpp.org/extensions/xep-0333.html §11) | Read state is a heuristic — "Bob has read up to seq N", never per-message truth |
| 4 | **Transport** | **WSS/443, length-delimited protobuf, ping 30–45 s** | Signal's "dual-purpose WebSocket" (`Signal-Server:.../RedisMessageAvailabilityManager.java:40-55`); Discord `wss://gateway.discord.gg/?v=10` | ~2–6 B/frame + one upgrade RTT, to keep the standard Ingress/SNI/L7 toolchain |
| 5 | **Timeouts** | **LB idle 30 min + TCP reset; nginx `proxy_read_timeout 120s`** | Azure LB **4-min default**, 4–100 range (https://learn.microsoft.com/en-us/azure/load-balancer/load-balancer-tcp-idle-timeout); nginx **60 s** default close (https://nginx.org/en/docs/http/websocket.html) | Ping must ship before anything else works. ⚠️ AKS annotation name UNVERIFIED |
| 6 | **Message IDs** | **Client UUIDv7 idempotency key + server per-recipient `seq`** | `insert_item.lua`: `HEXISTS guid` → return existing, else `HINCRBY counter` + `ZADD`, atomic (https://github.com/signalapp/Signal-Server/blob/main/service/src/main/resources/lua/insert_item.lua); Matrix "make the request idempotent"… "return the same HTTP response code and content" (`matrix-spec:.../_index.md:307-330`) | Two IDs/message + a unique-index probe per insert |
| 7 | **Ordering** | **Single-writer per recipient queue; plain integer `seq`** | Signal's per-device `HINCRBY` counter; Discord consistent hashing by channel ID. **No surveyed system uses vector/Lamport clocks for 1:1 chat** | Per-recipient row lock on enqueue |
| 8 | **Cursor semantics** | **Per-device cursor, `GREATEST(acked_seq, $seq)` — forward-only** | Iris: "separate pointers into the queue… When your phone is offline… the pointer stays in place while new messages can still be enqueued and other pointers advanced"; MAM no-holes / no-UID-reuse (https://xmpp.org/extensions/xep-0313.html §3.2) | Retention sweep must delete oldest-first only |
| 9 | **Backplane** | **Pub/sub carries a wake-up signal only; the queue is truth** | Signal `SPUBLISH` *after* the queue write (`insert_item.lua:24`); "makes a best effort… but **cannot guarantee at-most-one behavior**" (`RedisMessageAvailabilityManager.java:48-56`) | At-most-once pubsub ⇒ worst case a message is *late*, never lost |
| 10 | **Routing key** | **`(user_id, device_id)`; displace conflicts on connect** | Signal `record AccountAndDeviceIdentifier(UUID, **byte** deviceId)` + `ClientConnectedEvent{serverId}` → `handleConflictingMessageConsumer()` (`:85-105, :128-133`); MQTT 5 `0x8E Session taken over` [MQTT-3.1.4-3] | At-most-one is best-effort, as Signal states. `byte` implies a device cap |
| 11 | **Reconnect protocol** | **Jittered first heartbeat; cheap RESUME vs rate-limited IDENTIFY; `resume_gateway_url`** | Discord: jitter "meant to prevent too many clients from reconnecting at the exact same time"; "1000 IDENTIFY… does not include RESUME"; the 5M-session OOM cascade (https://docs.discord.com/developers/events/gateway, https://discord.com/blog/how-discord-scaled-elixir-to-5-000-000-concurrent-users) | Server retains resumable session state for a bounded window |
| 12 | **Overload control** | **Bounded-concurrency semaphore, fast-fail — not a circuit breaker** | Discord: "We didn't want to use a circuit breaker because we didn't want a burst in timeouts to result in a temporary state where no attempts are made at all" | Some requests rejected outright under load, by design |
| 13 | **Deploys** | **`preStop` staggered drain; grace period > drain window** | Discord ring-rebuild + reconnect-burst failure mode (same post) | Slower rollouts |
| 14 | **Delivered receipt** | **Server-generated, per-message** | `SERVER_DELIVERY_RECEIPT = 5` as an `Envelope.Type` (`Signal-Server:service/src/main/proto/TextSecure.proto:19`) | None material — you already own the per-device ack |
| 15 | **Read receipt** | **Client-generated up-to cursor, batched, monotonic-forward-only** | XEP-0333 "only move forward… MUST be ignored" (§5); Matrix "batched into one event per room and thread" (`receipts.md:195-199`) | Cannot reconstruct per-message read state |
| 16 | **Receipt privacy** | **Private read cursor from day one** | Matrix `m.read.private` v1.4: "Servers **MUST NOT** send… to any other user"; excluded from federation EDUs (`receipts.md:103-118`) | One extra receipt type now vs a fanout-path rewrite later |
| 17 | **Group receipts** | **Aggregate to `min(read_seq)`; degrade above a threshold** | XEP-0184 "NOT RECOMMENDED… one ack message from each occupant" (§5.3); ACS ships a **hard 20-participant cutoff** | No per-member ticks in large groups |
| 18 | **Tokens** | **Short-lived (5–15 min) aud-restricted EdDSA JWT + refresh; local verify** | RFC 9700 §4.10.2 audience restriction (https://www.rfc-editor.org/rfc/rfc9700.html#section-4.10.2); avoids making auth-service the §5 chokepoint | Revoked token lives until `exp`; add a Redis `jti` set when unacceptable |
| 19 | **Mid-connection expiry** | **`AuthExpiring` → `ReAuth` frame; never a scheduled disconnect** | MQTT 5 dedicated `AUTH` packet + `0x8C`; Matrix txn_id scope survives refresh (`_index.md:341-345`) | Gateway must support in-place security-context swap |
| 20 | **Password hashing** | **Argon2id m=19456 (19 MiB), t=2, p=1**, PHC string, ~250 ms calibration | OWASP, verbatim minimums; "increasing p does not… act as an iteration count"; "should take less than one second" (https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) | ~19 MiB RAM per concurrent login — size the login pool deliberately |
| 21 | **Email verification** | **Single-use URL token, hashed at rest, hard-coded base URL, `no-referrer`, per-account + per-IP limits, no account lockout** | OWASP "Use URL tokens for the simplest and fastest implementation"; "Accounts should **not** be locked out… can be used to deny access to users with known usernames"; consistent message **and** uniform timing (https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) | Cross-device UX friction. ⚠️ Specific expiry/attempt numbers UNVERIFIED — check NIST SP 800-63B |
| 22 | **Device identity** | **Server-minted `device_id` as a JWT claim; client may reclaim on re-login** | Matrix: "the act of logging in and out **creates a new device** (unless an existing `device_id` is given during the login process)" (`_index.md:336-341`); Signal's `byte deviceId` ordinal | Device cap; gateway must never trust a client-supplied device field |
